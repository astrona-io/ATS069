# Fast Feedback From Type Checks, Tests And Lint

A developer who waits ten minutes to learn that a change is wrong will make fewer, larger changes. A developer who learns in seconds makes many small ones. This part explains the checks of a Backstage workspace that give feedback in seconds, what question each one answers, and which questions none of them answers.

## Four sources of feedback

A Backstage workspace gives feedback from four places. The development server shows the running result. The type checker compares the code with the declared types. The test runner runs small programs that call your code and compare the result with an expected value. The linter reads the source text and reports patterns that the team has decided to avoid. Each one looks at the code from a different side, so a change can pass one and fail another.

In a project generated by Backstage, the root `package.json` defines scripts for these checks, for example `yarn tsc` for the type check, `yarn test` for the tests and `yarn lint` for the linter. A script name is only a name chosen by the project. The package definition says what a name runs. <!-- astrona:playground:renew -->

The practice workspace defines the same names in its own `package.json`, and you can read what each one runs:

```sh
cd /opt/portal
grep -A6 '"scripts"' package.json
```

## The type check answers a question about shapes

The TypeScript compiler, `tsc`, reads every file in the `include` list of `tsconfig.json` and checks that each value is used according to its declared type. The practice workspace runs it with `--noEmit`, which means it only reports errors and writes no JavaScript files. The check is fast because it does not start the application.

It catches a function called with the wrong arguments, a property that does not exist on a type, and a missing export. It cannot tell whether a function returns the right value, because a wrong value of the right type is still valid. The function `ownerState` returns one of three strings. A version that returns `'error'` where it should return `'missing'` passes the type check.

Run the type check on the working workspace:

```sh
yarn tsc
```

The command prints nothing and exits with status 0 when every file agrees with its types. Now open `packages/app/src/ownerWarning.ts` and replace `entity.spec?.owner` with `entity.owner`. Run `yarn tsc` again. The compiler reports that the property `owner` does not exist on the type `Entity`, and it names the file and the line. Restore the original line before you continue.

## The test answers a question about behavior

A test is a small program that calls your code with a chosen input and compares the result with the result you expect. The practice workspace uses the test runner that is built into Node.js. The test file `packages/app/src/ownerWarning.test.ts` has three tests: an entity with an owner, an entity without an owner and a missing entity. Run them:

```sh
yarn test
```

The runner prints one line for each test and a summary of passed and failed tests. Node.js 22 can run TypeScript files directly by removing the type annotations, which the script enables with a flag. This removal does not check types. Type checking stays the job of `tsc`.

Now make a change that the type check accepts and the tests reject. In `ownerWarning.ts`, change the returned value `'missing'` to `'error'`. Run `yarn tsc`: it passes, because `'error'` is a valid `OwnerState`. Run `yarn test`: the test for an entity without an owner fails and shows the expected and the received value. This is the main reason a workflow needs both checks. The type check guards the shape of data, and the test guards the meaning. Restore the file afterwards.

## Lint answers a question about team rules

A linter reads source text and reports patterns the team has decided to avoid, such as the type `any`, which turns the type check off for one value. Generated Backstage projects use ESLint for this. The practice workspace has a small script, `scripts/lint.mjs`, that checks three patterns: `: any`, `console.debug(` and `debugger`. It prints each match with the file and the line and exits with status 1 if it found any.

```sh
yarn lint
```

On the working workspace it prints `lint ok`. A lint rule never proves that code is correct. It enforces a convention, and some conventions exist because they prevented bugs in the past. Because the rules are plain text patterns here, you can read them in the script and see exactly what they match.

## Hot reload shows the running result

The development server is the fourth source of feedback. It watches the source files and updates the running program when a file changes. The word "hot reload" covers two different mechanisms. In the backend, a watcher restarts the whole process. In the browser, a frontend development server rebuilds the changed modules and updates the page, usually without a full page reload.

The practice workspace starts its backend with `node --watch`. This flag restarts the process when a file it loaded changes:

```sh
yarn start
```

Leave it running. In a second shell, edit the message in `packages/backend/src/index.ts` and save the file. The first shell prints the startup line again, because the watcher started a new process. Stop the process with `Ctrl+C`.

This feedback tells you that the program starts and runs. It does not tell you that the types agree or that the behavior is right. A page that renders after a hot reload can still hold a type error, because the development server may transpile code without checking its types.

## What each check can and cannot prove

| Check | Question it answers | It cannot show |
| --- | --- | --- |
| `yarn tsc` | Do values and types agree across packages? | That a value is the right one |
| `yarn test` | Does the code give the expected result for the cases written? | Cases nobody wrote |
| `yarn lint` | Does the code follow the team's rules? | That the code works |
| `yarn start` | Does the program start and respond? | Types, edge cases or production behavior |

None of them shows that a permission check is enforced, or that a remote system accepts your token. Those need a test with that system, or a review of the integration, and they are a separate piece of evidence.

## Run them in a useful order

The checks are independent, so order matters only for speed and for reading the result. Run the type check first, because one type error often explains several test failures. Run the tests next. Run the linter last, because its findings rarely change behavior. The helper `portal-check` in the playground runs the three checks in that order and prints one line for each.

```sh
portal-check
```

A line that starts with `ok` means the command exited with status 0. A line that starts with `FAIL` means it did not, and you run that one script alone to read its messages.

## Common pitfalls

> [!WARNING]
> A passing type check does not mean the behavior is right, and a refreshed page does not mean the types agree. Do not edit a test to make it pass unless the expected behavior itself changed. Do not silence the linter with `any` to make the type check pass: that removes the check for that value.
